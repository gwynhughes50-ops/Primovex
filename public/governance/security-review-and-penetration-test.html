1. Read this first: what this review is, and is not

This is an internal, AI-assisted security review and penetration test. It was carried out by an AI assistant working directly with the developer, using the source code and a local test copy of the database rules. It found real problems, most of which were fixed the same day, and it is useful evidence of the security work done. It is not an independent or accredited penetration test (for example CREST or CHECK), and it should not be presented as one.

What that means in practice:

•      The active attack testing ran against a local Firestore emulator loaded with the real access-rules file (firestore.rules), using simulated user identities. No production data was touched, and no test traffic was sent to the live system.

•      It tests the database access rules, which are the main barrier between one user and another user's data. It does not test Google's infrastructure, Firebase Authentication itself, the network, or the devices the app runs on.

•      The Cloud Functions were reviewed by reading the source and the fixes were deployed. They were not attacked live.

•      Not covered: network and infrastructure scanning, denial of service, social engineering, physical access, Windows or Android operating-system hardening, and any assessment of Google Cloud or the third-party services Primovex connects to.

•      Severity ratings in this report are the reviewer's judgement, not a formal scoring scheme.

If the practice's IG team or the health board requires independent assurance, the recommendation in section 8 is to commission an accredited test, scoped in proportion to the risk, alongside or after DPIA sign-off. This report should make that test quicker and cheaper by showing what has already been checked.

3. Scope and method

3.1 Static review

The source code was read for weaknesses in these areas:

•      Firestore security rules (who can read and write each collection).

•      Cloud Functions (the server-side code that runs with administrator power and bypasses the rules).

•      Client-side code: cross-site scripting (XSS) in printing and rendering, and secrets held in the app.

•      Session and idle-lock handling, including how the lock PIN is stored.

•      Desktop app hardening (Tauri configuration, Content-Security-Policy).

•      Third-party dependencies (npm audit on the app and on the Cloud Functions).

•      Role and capability enforcement across every page, tab and route (the access-control audit).

3.2 Active penetration test of the access rules

A local Firebase emulator was started with the real firestore.rules file. Test identities were created for each kind of user: System Admin, Practice Manager, an ordinary User, ReadOnly, Partner, Reception, a custom role with SAR access, a custom IT role, an unauthenticated visitor, and a stranger with a fresh account. Each test then tried something the rules should refuse (or, equally important, something they should still allow). A check passes only when the rules behave as intended.

The suite tries, among other things: giving yourself extra permissions, changing your own role, reading or editing records you have no relationship to, claiming someone else's invitation, creating a profile without being an administrator, reading data while signed out, crossing between sites, and using a custom role that holds an administrator-looking capability. The full list of 441 checks is in Appendix A.

All identities and records were synthetic. Nothing in the tests contains real patient, staff or complainant data.

The sidebar hid links, but a signed-in user could still open the address directly. The full audit is a separate document (Access Control Audit); this table records what was found and what was done.

6. Security controls in place at the date of this report

Control

How it is done

Who can sign in

Firebase Authentication. Accounts are created only by an administrator through a server-side Cloud Function. Self-registration is closed in the database rules (tested). If an administrator needs to help someone back in, the app generates a one-time password link through an administrator-only, audited Cloud Function.

Who can do what

Role-based, with each role holding a list of capabilities. The same role-to-capability mapping is enforced in three places that mirror each other: the app, the database rules, and the Cloud Functions. Custom roles are supported and tested.

Sensitive records

SARs and Concerns are visible only to the relevant team, to people named on a case, and (read-only) to oversight partners. Activity and timeline entries can be added but never edited or deleted, and deleting a SAR is limited to the SAR team and recorded. These rules are covered by the attack suite.

Where data is held

Firestore database in the EU multi-region (eur3). Cloud Functions in europe-west2 (London).

Recovery

Database delete protection on. Point-in-time recovery on (7-day window).

Sessions

Automatic lock after 15 minutes of inactivity on both desktop and mobile, unlocked by a PIN. Absolute session limit of 12 hours, after which the person is signed out. The PIN is a convenience lock against someone walking up to an unattended device; it is not encryption of data held on the device.

Desktop app hardening

Content-Security-Policy enabled: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self' https://*.googleapis.com https://europe-west2-medtrak-b1cad.cloudfunctions.net; object-src 'none'; base-uri 'self'; form-action 'self'. Scripts may load only from the app itself. Inline styles are still allowed, which is a known, lower-risk exception.

Output safety

Printed documents (QR labels, Concerns case summary) escape all values before writing them into the page.

Third parties

QR codes are generated on the device. No patient or staff data is sent to any third party by this feature.

Audit trail of changes to a concern (added 29 Oct 2026)

Every change to a concern case is written as a history line that nobody can edit or delete (tested). The screen shows it to the concerns team only; the database lets anyone who can read the case read it (SR-14). If a line cannot be written, the person is told on the screen.

ClinFlow safeguards

The server refuses a letter unless the caller has the capture permission and has confirmed it is an invented test letter; accepts only a PDF of up to 4 MB with a valid file header; and keeps metadata only, never the letter or its text. The database accepts only records marked as test data and refuses the app any access to the analysis records. See section 9.

Files read and written by the desktop app

Only in folders the person chose, through commands that name a letter by id and one of three file names, or a scan by bare name and a kind, never a path. Sizes and formats are checked, a file is written to a temporary name and moved into place, and the commands are not in the Android build. See section 9.

Installer and updates

The app's own updates are signed and checked against a public key before they are installed. The first Windows installer is not code-signed (SR-17).

Other checks made between 18 and 21 September

•      Hostile input in printing. The Concerns case-summary print was tested with values containing script and image-error tags. Nothing executed and nothing was created; the values printed as plain text.

•      Save-retry changes do not hide real refusals. A change to stop duplicate records when a connection drops was tested against the real rules on records that cannot be edited after creation. SR-15

Case histories could not be read until 30 October 2026. The database was missing the indexes that four lists need (concern history, learning actions, correspondence, significant event history). Every read failed and the screens and printouts showed nothing. The records were saved and nothing was lost; this is about availability and completeness of the record, not confidentiality.

Medium

Fixed 30 Oct 2026

Four indexes added and deployed; a test keeps all ten in the project; a failed audit write now warns the person on the screen. A query that works in the emulator and in demo mode can still fail on the live database.

SR-16

New dependency advisories since 21 September. Found 4 November 2026: the app 14 (1 critical, 6 high, 7 moderate); the Cloud Functions 10 (1 critical, 2 high, 7 moderate). The two critical ones were dompurify in the app (reached only through the PDF library, and it concerns a sanitising hook the app does not use as far as this review found) and proxy-addr in the Cloud Functions (reached through the server inside Firebase Functions, and it concerns trusting a visitor's IP address, which no Primovex function does as far as this review found). Most of the rest are denial-of-service issues or build tools. After the safe update of 4 November 2026: the app has 10 (4 high, 6 moderate) and the Cloud Functions 6 (all moderate). The 4 high in the app are all in the Firebase client libraries (@firebase/firestore, @grpc/grpc-js), where no fixed release is available in the current Firebase version line; the moderate ones are react-router (R2) and build and transitive tools.

Low to Medium (exposure believed low, not proven)

Partly fixed 4 Nov 2026

A safe update (npm audit fix, no forced upgrades) was applied to the app and the Cloud Functions, tested (all tests, the 256 Cloud Functions tests, the build and the 441-check attack suite) and released on 4 November 2026 (version 0.15.119, with the Cloud Functions redeployed). Re-check after each Firebase update; the react-router item (R2) needs a larger upgrade.

SR-17

The Windows installer is not code-signed. Windows Defender flagged an earlier unsigned build as suspicious (a machine-learning false positive, submitted to Microsoft). In early November 2026 an NHS device reported a threat alert and NHS Wales OneDrive refused to sync an installer; the alert's name has not been obtained.

Medium

Open

A code-signing certificate is being obtained. Until then NHS IT verify each installer against its published SHA-256 fingerprint. The app's own update package is signed and checked before it is installed, which protects updates but not the first installer.

Appendix B. How to reproduce the test

•      The suite is stored in the Primovex repository at docs/security/attack-suite (with a short README), and a copy is supplied with this report.

•      Install Java and the Firebase CLI. In that folder run npm install, which installs @firebase/rules-unit-testing and the firebase library.

•      Start the emulators from the repository root: firebase emulators:start --only auth,firestore,storage. The suite expects Firestore on 127.0.0.1, port 8080, and Storage on port 9199.

•      Run the suite: npm test. It loads firestore.rules from the repository, empties the emulator, creates its own synthetic users and records, and prints one line per check. It can be run repeatedly against the same emulator (checked with three consecutive runs on 21 September 2026).

•      A healthy run ends with 441 passed, 0 failed (as on 4 November 2026). Any failure means a rules change has opened access that should be closed, or has closed access that a legitimate role needs. The check marked KNOWN GAP is expected to pass until SR-14 is closed.

•      The suite uses only synthetic data and needs no credentials. It never contacts the live database.
